A security tool that runs green without checking anything is worse than none: it creates trust that carries nothing.

That is why the counterproof is not an extra in Chinook Security but the core — every rule is run against a deliberately broken case, and every check against a deliberately broken bot.

Installing

Into the repository you want checked, as .github/workflows/chinook.yml:

name: Chinook Security
on: [pull_request]

permissions:
  contents: read

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0          # only needed for the history check

      - uses: Pheonix-Studio-cat/Chinook-security/actions/secret-bot@main
        with:
          history: "true"
      - uses: Pheonix-Studio-cat/Chinook-security/actions/workflow-bot@main
      - uses: Pheonix-Studio-cat/Chinook-security/actions/dependency-bot@main
      - uses: Pheonix-Studio-cat/Chinook-security/actions/code-bot@main
      - uses: Pheonix-Studio-cat/Chinook-security/actions/license-bot@main

@main is for trying it out. For day-to-day use, pin a commit SHA — exactly what the workflow bot demands of every other action.

Exit codes

ValueMeaning
0nothing found that reaches the threshold
1findings at or above the threshold
2the run could not determine anything — e.g. OSV was unreachable

The 2 is the reason it exists: a request that did not get through is not an empty result. It does not count as passing.

The overseer

The AI layer. It rates every finding — confirmed, probably-real, probably-noise, unclear — and gives a sentence or two of reasoning.

No finding gets lost. The model’s answer can only attach a triage field to a finding. It cannot remove one, change a severity, or invent one.

And that is in the code, not in the prompt: the result list is built from the findings, never from the answer. A guarantee that hangs on a model’s obedience is not one.

PropertyWhy
It does not spend someone else’s money The key comes from CHINOOK_AI_TOKEN in the repository of whoever runs it. Chinook Security holds none.
It is optional Without a key everything else keeps running. A scanner that fails because a model did not answer is worse than none.
No tools, no write access It inevitably reads foreign text. A model with tools reading such text is prompt injection with write access.

The counterproof

It copies the repository, breaks the bots on purpose — redaction switched off, a rule skipped, the network error swallowed, the overseer dropping findings — and demands that the checks go red as a result. If they stay green, the check is worthless, and the counterproof says so.

The finding format

Every bot emits the same thing — as JSON and as SARIF for GitHub’s security view. Without it neither the overseer nor this page could be built, because both read findings and not tool output.

Fields per finding: id, bot, rule, title, severity, confidence, location, explanation, remediation, evidence, fingerprint.

evidence describes a find without reproducing it — no prefix, no hash, only rule and length. A prefix would be a leak for a password, a hash an oracle for a weak one, and in a public repository anyone can read the action log.

What Chinook Security does not promise

  • Completeness. No finding does not mean „secure“, it means „these rules found nothing“.
  • No false positives. Several rules run at medium confidence and are sometimes wrong.
  • No detection rates. There are no percentages here, because there is no measurement backing them.
  • No legal advice and no severity rating of its own.

The limits in detail are in docs/grenzen.md (German) — that file matters more than a feature list.
